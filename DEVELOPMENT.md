# Development

## Make targets

The `Makefile` is generated by [bmk](https://pypi.org/project/bmk/) (its first line reads
`# BMK MAKEFILE <version>`) and is rewritten when bmk updates it, so this page does not copy its
target list. `make help` prints every target with its description.

The targets used day to day:

| Target                                          | What it does (from the Makefile's `##` comments)                  |
|-------------------------------------------------|-------------------------------------------------------------------|
| `make dev`                                      | `uv pip install -e ".[dev]"`: editable install with the dev tools |
| `make install`                                  | `uv pip install -e .`: editable install without dev tools         |
| `make test`                                     | run the test suite (the full local gate, see below)               |
| `make test-all`                                 | run pytest and pyright on every declared Python version           |
| `make testintegration`                          | run only the integration tests (they call the live GitHub API)    |
| `make run ARGS="..."`                           | run the project CLI with the given arguments                      |
| `make build`                                    | build wheel and sdist                                             |
| `make clean`                                    | remove build artifacts and caches                                 |
| `make bump-patch` / `bump-minor` / `bump-major` | bump the version (`make bump` is `make bump-patch`)               |
| `make commit MSG="..."`                         | create a git commit                                               |
| `make push MSG="..."`                           | run the tests, commit and push                                    |
| `make release`                                  | create a versioned release (tag and GitHub release)               |
| `make ship`                                     | push, wait for CI, release, wait for the release CI               |
| `make codecov`                                  | upload the coverage report to Codecov                             |

Pass a commit message with `MSG="..."`: the Makefile exports it as `BMK_COMMIT_MESSAGE`, so
punctuation and `$` reach git unchanged. Without one, `make commit` / `make push` prompt for it on
a terminal and use `chores` when not on a terminal. When nothing is staged, the commit is created with `--allow-empty`.

## What `make test` runs

`make test` runs bmk's test pipeline. First, one at a time: a dependency update, `uv lock`,
the ruff formatter and ruff's autofix. Then, side by side: bandit, import-linter (the contract in
`[tool.importlinter]`), pip-audit, pyright (strict mode), pytest with coverage (doctests included),
the ruff format and lint checks, and shellcheck / PSScriptAnalyzer where such scripts exist.
Because the first stages write files, `make test` can change the working tree; check
`git status` afterwards.

Tests marked `integration` are excluded from `make test` and from CI. They live in
`tests/test_github_integration.py`, are also marked `local_only`, skip whenever the `CI`
environment variable is set, and need `SECRET_GITHUB_OWNER` and `SECRET_GITHUB_TOKEN`. Run them
with `make testintegration`; they re-enable the configured account's workflows.

`pytest` skips the doctests of `src/keep_github_workflows_active/keep_github_workflow_active.py`
(`--ignore` in `[tool.pytest.ini_options] addopts`), because they call the live GitHub API.

### Dependency auditing

pip-audit fails the run on any known vulnerability except those listed, with a reason each, in
`[tool.pip-audit] ignore-vulns` in `pyproject.toml`.

## Versioning and metadata

- `[project].version` in `pyproject.toml` is the single source of truth.
- `src/keep_github_workflows_active/__init__conf__.py` holds the same metadata as plain constants
  (name, title, version, homepage, author, console-script name). bmk rewrites it from
  `pyproject.toml` during `make bump-*` and before `make commit` / `make push`; never edit it by
  hand.
- Write changelog entries under `## [Unreleased]` in `CHANGELOG.md` before bumping.

## CI and publishing

| Workflow                                       | Runs on                               | Does                                                                                                    |
|------------------------------------------------|---------------------------------------|---------------------------------------------------------------------------------------------------------|
| `.github/workflows/default_cicd_public.yml`    | push, pull request, daily 03:17 UTC   | tests on the matrix from the pyproject classifiers and `[tool.ci].os`, pipx/uv install check, notebooks |
| `.github/workflows/default_release_public.yml` | push of a `v*` tag, manual dispatch   | builds and publishes to PyPI                                                                            |
| `.github/workflows/codeql.yml`                 | push, pull request, Mondays 08:00 UTC | CodeQL analysis                                                                                         |
| `.github/workflows/activate_workflows.yml`     | push, pull request, Fridays 03:47 UTC | tests; on the schedule only, runs `enable-all-workflows` and `delete-old-workflow-runs`                 |

The release workflow publishes with the `PYPI_API_TOKEN` secret when it is set, and otherwise
through a PyPI Trusted Publisher (OIDC, environment `pypi`).

To publish a release:

1. Add the changelog entries under `## [Unreleased]`.
2. `make bump-patch` (or `bump-minor` / `bump-major`).
3. `make release` tags the commit `v<version>` and creates the GitHub release; the tag push
   starts the release workflow.

### Codecov

`make codecov` uploads the coverage report. For a private repository set `CODECOV_TOKEN` in your
environment or in `.env` (see `.env.example`).
